<field_definitions>
document_relevance:
- "relevant" if at least one event is extracted.
- "not_relevant" if no event is extracted.

event_type:
- Must exactly match one allowed event_type value.
- If multiple labels seem possible, choose the most specific label directly supported by the grounding_quote.
- Remove the event if no allowed label is clearly supported.

location_text:
- Copy the place name that best anchors where the event happens.
- Prefer named places: countries, provinces, cities, districts, camps, border crossings.
- Do not use vague spatial or relational phrases such as "across the border", "nearby", "in the area", "outside the city", or "close to the coast" if a named place is available.
- For migration events, use the origin location for an origin crisis and the destination location for an arrival or influx event.
- If no explicit named event location is given, use "not_stated".

event_time:
- The normalized, machine-parseable time or date for the event.
- Do not simply copy the time phrase from the article when it can be normalized.
- Infer the real event date/time whenever possible using only:
  - the event-specific wording in the article;
  - the article publication date, if explicitly included in the input text;
  - calendar logic for relative expressions.
- Do not use world knowledge, external sources, URLs, filenames, or metadata outside the input text.
- Use the most precise grounded value possible.
- Use ISO-like formats:
  - Year: YYYY
  - Month: YYYY-MM
  - Day: YYYY-MM-DD
  - Year range: YYYY-YYYY
  - Month range: YYYY-MM/YYYY-MM
  - Day range: YYYY-MM-DD/YYYY-MM-DD
  - Open-ended start: YYYY-
  - Open-ended end: -YYYY
- Normalize absolute expressions:
  - "from 1992 to 1996" -> "1992-1996"
  - "between 1992 and 1996" -> "1992-1996"
  - "as of mid-2018" -> "2018"
  - "in 2018" -> "2018"
  - "in March 2018" -> "2018-03"
  - "on 12 March 2018" -> "2018-03-12"
  - "since March 2018" -> "2018-03-"
  - "before 2018" -> "-2018"
  - "after 2018" -> "2018-"
- Normalize relative expressions using the article publication date when it is explicitly included in the input text:
  - If the publication date is 2018-07-15, then "last month" -> "2018-06"
  - If the publication date is 2018-07-15, then "this month" -> "2018-07"
  - If the publication date is 2018-07-15, then "this year" -> "2018"
  - If the publication date is 2018-07-15, then "yesterday" -> "2018-07-14"
  - If the publication date is 2018-07-15, then "today" -> "2018-07-15"
  - If the publication date is 2018-07-15, then "tomorrow" -> "2018-07-16" only when the event is forecast or projected.
  - If the publication date is 2018-07-15, then "next month" -> "2018-08" only when the event is forecast or projected.
- For weekday expressions such as "on Tuesday":
  - Resolve to the closest matching calendar date not after the publication date, unless the article clearly indicates a future event.
  - If the publication date is Sunday 2018-07-15, then "on Tuesday" -> "2018-07-10" unless future wording is explicit.
- For vague but directional expressions:
  - "recently" -> "not_stated" unless the article gives a more specific anchor.
  - "in recent years" -> "not_stated" unless the article gives a bounded range.
  - "for decades" -> "not_stated" unless the article gives a start year or range.
  - "during the rainy season" -> "not_stated" unless the article explicitly defines the season dates.
  - "currently", "now", "still", or "ongoing" -> use the article publication date if the event is clearly current at publication time; otherwise use "not_stated".
- If the article gives a duration and an anchor, normalize to a range when possible:
  - If publication date is 2018-07-15, "over the past two weeks" -> "2018-07-01/2018-07-15"
  - If publication date is 2018-07-15, "over the past year" -> "2017-07/2018-07" unless exact day precision is clearly intended.
- If the article gives a time expression with lower precision, do not invent higher precision:
  - "mid-2018" -> "2018"
  - "early 2018" -> "2018"
  - "late 2018" -> "2018"
  - "summer 2018" -> "2018" unless the article explicitly defines the season dates.
- If no event-specific time is stated, use "not_stated".
- Do not include filler words such as "from", "to", "as of", "around", "during", "since", "last", or "next" in event_time unless the expression cannot be normalized and is still useful.
- If a time expression cannot be normalized but is explicitly event-specific and useful, copy the shortest useful time phrase from the article.
- If a non-normalized time phrase would not be useful for downstream parsing, use "not_stated".

time_status:
- "past" if the event clearly happened before the article's publication date and is completed or historical.
- "ongoing" if the event is continuing, current, rising, still happening, or affecting people at the article's publication date.
- "forecast" if the event is expected, projected, warned about, or likely to happen after the article's publication date.
- "not_stated" if the article does not provide enough information.
- Base this only on article wording, the explicitly provided publication date in the input text, and the normalized event_time.
- Do not infer time status from world knowledge.

affected_entity:
- The thing, system, asset, or livelihood affected.
- Examples: "food and medicine", "healthcare system", "water supply", "maize crop", "roads", "aid supplies".
- If absent, use "not_stated".
- If this field does not make sense for the event, use "not_applicable".

affected_group:
- The people or population group affected.
- Examples: "farmers", "children", "refugees", "pastoralists", "Venezuelan migrants".
- If absent, use "not_stated".
- If this field does not make sense for the event, use "not_applicable".

severity:
- "low" for limited or mild impact.
- "medium" for meaningful but not severe impact.
- "high" for severe or large-scale impact.
- "extreme" for catastrophic, emergency, collapse-level, or massive impact.
- "not_stated" if severity cannot be grounded from the article.
- Base severity only on article wording and stated figures. Never infer severity from world knowledge.

modality:
- "asserted" if the article states the event as a fact.
- "reported" if the event is attributed to a source, authority, official, or organization.
- "projected" if the event is expected or projected in the future.
- "hedged" if the event is uncertain, possible, suspected, or conditional.

grounding_quote:
- Must be one exact, contiguous span copied from the article.
- Must be sufficient to justify the event_type.
- Prefer the shortest local quote that clearly supports the event.
- The quote may also include the source wording used to normalize event_time when helpful.
- Do not paraphrase.
</field_definitions>
